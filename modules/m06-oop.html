Classes without Java ceremony

A Python class is a namespace plus behavior; it does not need fields declared up front.

Java asks you to declare structure before use. Python lets __init__ bind instance attributes directly. The tradeoff is social and tooling discipline: clear constructors, type hints, dataclasses, and tests replace compiler-enforced field declarations.

Java
public final class Money {
    private final String currency;
    private final int cents;

    public Money(String currency, int cents) {
        this.currency = currency;
        this.cents = cents;
    }
}
Python
class Money:
    def __init__(self, currency: str, cents: int) -> None:
        self.currency = currency
        self.cents = cents
Idiomatic Python
Python
class Money:
    def __init__(self, currency: str, cents: int) -> None:
        if cents < 0:
            raise ValueError("cents must be non-negative")
        self.currency = currency
        self.cents = cents

    def format(self) -> str:
        return f"{self.currency} {self.cents / 100:.2f}"

print(Money("USD", 1299).format())
Coming from Java: Unlearn writing JavaBean boilerplate. Python does not reward a file full of get_currency and set_currency methods.
Under the hood

Attribute lookup checks the instance, then class, then base classes according to the method resolution order.

Properties replace getters and setters

Python exposes attributes first and adds managed access later without changing callers.

In Java, encapsulation often means private fields plus accessors from day one. In Python, public attributes are normal. If validation or computed behavior appears later, @property preserves the attribute syntax.

Java
public int getCents() { return cents; }
public void setCents(int cents) {
    if (cents < 0) throw new IllegalArgumentException();
    this.cents = cents;
}
Python
class Invoice:
    @property
    def total(self) -> int:
        return self._total
Idiomatic Python
Python
class Account:
    def __init__(self, balance: int) -> None:
        self.balance = balance

    @property
    def balance(self) -> int:
        return self._balance

    @balance.setter
    def balance(self, value: int) -> None:
        if value < 0:
            raise ValueError("balance cannot be negative")
        self._balance = value

acct = Account(10)
acct.balance += 5
print(acct.balance)
Coming from Java: Unlearn defensive accessor generation. Start with attributes; upgrade to properties when there is a reason.
Under the hood

property is a descriptor: its __get__ and __set__ methods participate in normal attribute lookup.

Exercises

Make read-only
Define only @property and no setter.
Computed property
Add dollars returning cents / 100.

Protocols and dunder methods

Python polymorphism is usually behavioral: if an object supports the operation, it fits.

Java formalizes contracts through interfaces. Python formalizes many contracts through special methods such as __len__, __iter__, __eq__, and __enter__. Static typing can express this with Protocol, but runtime code typically just performs the operation.

Java
interface Priced {
    int cents();
}
int total(List<? extends Priced> items) { ... }
Python
from typing import Protocol

class Priced(Protocol):
    cents: int
Idiomatic Python
Python
from dataclasses import dataclass

@dataclass(frozen=True)
class Money:
    cents: int

    def __add__(self, other: "Money") -> "Money":
        return Money(self.cents + other.cents)

print(Money(5) + Money(7))
Coming from Java: Unlearn asking where the interface file is. The more Pythonic question is which operation the caller needs.
Under the hood

Dunder methods are looked up on the type for many operations, which is why monkey-patching them on one instance rarely works.

Class methods, static methods, and alternate constructors

Python class methods receive the class object and are ideal for named constructors.

Java often uses overloaded constructors, static factories, or builders. Python has no overloads by signature. Use clear classmethod constructors, module functions, or dataclasses instead of factory hierarchies.

Java
public static Money dollars(int dollars) {
    return new Money("USD", dollars * 100);
}
Python
class Money:
    @classmethod
    def dollars(cls, amount: int) -> "Money":
        return cls("USD", amount * 100)
Idiomatic Python
Python
class Money:
    def __init__(self, currency: str, cents: int) -> None:
        self.currency = currency
        self.cents = cents

    @classmethod
    def from_decimal(cls, currency: str, text: str) -> "Money":
        whole, _, frac = text.partition(".")
        return cls(currency, int(whole) * 100 + int((frac + "00")[:2]))

print(Money.from_decimal("USD", "12.30").cents)
Coming from Java: Unlearn building AbstractFactory layers before plain constructors and named constructors have failed.

Exercises

Add from_dollars
Return cls('USD', dollars * 100).
Choose staticmethod
Use it only when the function belongs near the class but needs neither self nor cls.

Multiple inheritance and MRO

Python supports multiple inheritance, but cooperative design matters more than clever hierarchy.

Java avoids multiple implementation inheritance and uses interfaces. Python allows it and resolves methods with C3 linearization. Mixins can be useful when they are small, stateless, and cooperative with super(). Deep hierarchies are still a smell.

Java
class Service implements Auditable, Cacheable {
    // Java composes most behavior explicitly.
}
Python
class JsonMixin:
    def as_json(self) -> str:
        return "{}"

class Report(JsonMixin):
    pass
Idiomatic Python
Python
class A:
    def ping(self) -> list[str]:
        return ["A"]

class B(A):
    def ping(self) -> list[str]:
        return ["B", *super().ping()]

class C(A):
    def ping(self) -> list[str]:
        return ["C", *super().ping()]

class D(B, C):
    pass

print(D().ping())
print([cls.__name__ for cls in D.mro()])
Coming from Java: Unlearn using inheritance as the first reuse tool. Composition, functions, and small protocols usually age better.
Under the hood

C3 linearization preserves local precedence order and monotonicity, preventing ambiguous parent ordering.

Exercises
